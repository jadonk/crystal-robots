Building crystal-robots

A robot battle game, a compiler to WebAssembly, and the robots that fight in your browser, built one commit at a time.

Open the play page and a battle is already running: four robots, each a few dozen lines of code, scanning, driving and firing at each other on a thousand-meter square. Click one and you can peel it apart: its source, the steps the compiler took to understand it, and the WebAssembly it became. Or go to the challenge and write your own, one level at a time, until it is good enough to enter a tournament.

This post is the story of how that was built, one commit at a time, and how you can rebuild it yourself.

Where this comes from

In 1985 Tom Poindexter released CROBOTS, “a programming game, for programmers (or aspiring programmers.)”. You wrote a robot in a small subset of C; CROBOTS compiled it for its own little virtual machine and set it loose on a battlefield against up to three others. The robots had a scanner, a cannon and a drive, and everything else was up to you. Its rules, its physics and even its arithmetic quirks are the rules here.

In 2019 Colin Eberhardt wrote a blog post and a small language called chasm: a compiler to WebAssembly built from nothing, one step at a time, each step linked to a commit you could check out. That post is the model for this one. crystal-robots's WebAssembly encoder started as a port of chasm's.

And Crystal, a language that reads like Ruby but compiles to fast native code, is what it is written in. A Ruby-like robot language implemented in a Ruby-like systems language turns out to be a good fit: the robot code a beginner writes and the compiler code that reads it look like relatives.

Reading Crystal

Crystal is the language used to build this project. These small shapes are enough to follow the changes below. A spec is a test: a small program that checks an expected result.

Bring in a file: require

require "./compiler/parser"

Use code written in another file.

Name an action: def … end

def double(n)
  n + n
end

Give a group of steps a name so it can be used again.

Group code: class and module

module Compiler
  class Parser
  end
end

A module groups related names; a class describes an object that can hold data and actions.

Keep a value: @name

@program = program

The @ keeps a value with one object for later use.

Say what kind of value: : Int32

def add(n : Int32) : Int32

Int32 means a whole number stored in 32 bits; the marks say what kind comes in and goes out.

Repeat steps for each item: do |x| … end

numbers.each do |x|
  puts x
end

Run the indented steps once for each item, calling the current item x.

Put a value in text: #{x}

puts "robot #{name}"

Crystal replaces #{name} with the current value of name.

Use a label: :name

mode = :trace

A symbol is a short, fixed label used to choose a case or name a rule.

Check a result: describe, it, should

describe "addition" do
  it "adds" do
    (2 + 3).should eq(5)
  end
end

These group a test, name what it checks, and say what answer is expected.

Write bytes: Bytes[…]

Bytes[0x00, 0x61]

Bytes are small numbers written directly into a file; 0x marks a number written in base 16.

Pass a turn: Channel

ready.send(nil)
ready.receive

One task sends a signal and another waits to receive it before continuing.

Chapter 1 · Phase A: a compiler to WebAssembly

Phase A follows chasm's own path, step by step: an empty module, a hand-written function, then a real compiler that grows one language feature per commit, plus the two things a robot language needs that chasm does not: host builtins for sensing and acting, and a checker that explains mistakes. By the end, a robot program can be traced, checked, interpreted and compiled from the command line, and two independent engines agree on what it does.

Phase A.3: a hand-assembled add function

Commit 27a3ab6

Before writing a compiler, it helps to write by hand what the compiler will eventually write for you. This commit assembles a module containing one function, add, which takes two 32-bit integers and returns their sum. A module is a list of sections: a type section describes the function's signature (i32, i32) -> i32, a function section declares that function 0 has that type, an export section gives it the name add so the outside world can call it, and a code section holds its body.

That body is four instructions, and it shows the most important idea in WebAssembly: it is a stack machine. local.get 0 pushes the first argument onto a stack, local.get 1 pushes the second, i32.add pops both and pushes their sum, and whatever is left on the stack at end is the return value. Every program this compiler ever produces will be built from that same push-and-pop pattern.

To actually run the module, the specs use wasmer, a WebAssembly runtime with a Crystal binding (pinned at 4.4.0). Not every machine has wasmer's library installed, so the wasmer specs are opt-in: crystal spec -Dwasmer runs them, and plain crystal spec reports them as pending rather than silently skipping them. That pattern repeats for every optional tool from here on.

Phase A.4: the multipass tokenizer and a real compiler for puts NUMBER

Commit 0b60f75

This is where crystal-robots stops following chasm closely. chasm has a classic compiler front end: a tokenizer that chops source text into words (“tokens”), then a parser that assembles those tokens into a tree. crystal-robots uses a different idea, worked out in docs/PARSER.md: a multipass tokenizer.

Pass 0 turns the source into a string of single-character symbols, called glyphs here: a number becomes №, the word puts becomes ∊, a line break becomes ⏎. Every later pass looks for the first rule in a list (GRAMMAR) that matches somewhere in that string and replaces every match with a single new glyph that stands for the bigger piece. The program is understood when the whole string has collapsed to one glyph, ⏹, the program. Three rules are enough for a program made of puts 42 lines:

The appeal is that you can watch it work. -t prints the string after every pass, so the whole parse is a short list of lines you can read top to bottom. (The maintainer's own note in this commit is worth repeating: the lexing pass and the grammar passes ended up in two different loops, and a single loop would be easier for a new programmer to hold in their head. That tension, simple to explain versus simple to implement, comes back throughout.)

The emitter, the part that writes WebAssembly, now walks the result instead of hand-assembling bytes. For each puts it emits three instructions: push the number, call an import named env.puts (a function the host provides, in this case the spec), and drop the result. puts returns its argument instead of nothing, partly to dodge a crash in the wasmer binding on imports with no result, and partly because later, when robots call builtins like scan for their value, every builtin will return something anyway.

Phase A.5: binary expressions

Commit 613e895

Arithmetic: + - * / // %, parentheses and unary minus. The interesting part is precedence, the rule that 2 + 3 * 4 is 14, not 20. In a pass-based parser, precedence falls out of rule order and a few guards: the multiply rule only fires when it cannot steal an operand from a tighter operator, add only fires after multiply is done, and parentheses reduce before either. Both are left associative, so 10 - 3 - 2 means (10 - 3) - 2.

One shortcut is taken on purpose and written down: for now / and // both truncate toward zero, which is what WebAssembly's i32.div_s does. CROBOTS's own rules (division that rounds down, and dividing by zero gives zero rather than crashing) wait until a robot can actually divide by something that might be zero.

Phase A.6: global variables and assignment

Commit 2ae5e05

Robots need memory between turns, so the language gets variables. A CROBOTS-style robot declares its long-lived state up front with global(name, initial value); plain assignment with = changes it. In WebAssembly, each one becomes a global, a named slot the module keeps for as long as it runs. Assignment compiles to global.set followed by global.get, so the assigned value is also left on the stack, which is what lets a = b = 3 work later.

The grammar rule for assignment only fires once the right-hand side is a complete expression followed by a line break. That kind of lookahead, “only match if what follows is X”, is how the pass-based parser avoids grabbing half an expression too early.

Phase A.9: the CROBOTS builtins as host imports

Commit abf7f9b

A robot's whole job is calling a small set of built-in functions: scan to look for enemies, cannon to shoot, drive to move, damage, speed, loc_x and loc_y to sense itself, plus math helpers. None of those can be written in the robot language itself. They belong to whatever is running the robot: a test, an interpreter, eventually a battlefield.

So each builtin becomes a WebAssembly import: the module says “I need a function called env.scan that takes two numbers and returns one”, and the host supplies it. Every builtin is typed by how many numbers it takes (zero, one or two) and returns one. A module only imports the builtins its program actually calls, in a fixed order, so two programs that use the same builtins get identical import sections. There is no battlefield yet, so the spec's stand-in host returns fixed made-up numbers for the sensors and just adds up the arguments of the actions.

Phase A.10: user-defined functions

Commit 7fbce2e

def, calls with arguments, and return. Each def compiles to its own WebAssembly function; parameters become locals, and a name assigned inside a function that is not a global becomes another local.

Writing the recursion test turned up a real ambiguity in the glyph grammar. Inside n * fact(n - 1), the multiply rule saw fact as an ordinary value and grabbed it before the call rule ever got to see the whole fact(n - 1). The fix is one line in the definition of “a value”: a name immediately followed by an opening parenthesis is never a value, because it is always a call waiting to be reduced.

№ is a number, 😑 an already-reduced expression, 𝑥 a name and ⟮ an opening parenthesis; (?!⟮) means “not followed by an opening parenthesis”. The spec now computes fact(5) == 120.

Phase A.13: the reference interpreter

Commit f0e79e1

An interpreter runs a program directly from its tree, one node at a time, instead of turning it into machine code first. crystal-robots gets one here for a very practical reason: having two independent ways to run the same program lets each check the other.

Every builtin goes through a Host, an interface that something else implements. NullHost is a stand-in with the same made-up behavior the WebAssembly specs' host already has. break and return are implemented with Crystal exceptions inside the interpreter, which is simple and works well natively. The payoff is spec/differential_spec.cr: three programs covering arithmetic, globals, every loop and branch, functions, recursion and builtins run through both the interpreter and the compiled WebAssembly, and must print exactly the same thing. Two separately written readings of the same tree agreeing is a stronger signal than either one's own tests.

Phase B.5: logical and/or and bitwise xor

Commit 610e3b5

&&, || and ^. Following CROBOTS, both sides of && and || are always evaluated (no short-cut when the left side already decides the answer), and the result is 0 or 1. ^ is bitwise exclusive-or, applied to the raw numbers: 6 ^ 3 is 5.

This commit also records a real problem in the test setup. Phase C.1: cycle charging

Commit 715ddde

In CROBOTS, robots don't run as fast as the computer allows. They take turns, and each turn is a budget of virtual cycles: reading a value costs one, an operator one, a builtin call two, a call to your own function three. That is what makes a clever robot different from a busy one, and it is what makes battles fair.

The WebAssembly side has to agree, or a compiled robot would get more or fewer turns than an interpreted one, so the emitter can now import env.tick and call it with the number of cycles to charge at exactly the places the interpreter charges them. The differential specs gain a check that both engines charge identical totals.

Phase C.5: interleaving robots into real matches

Commit 87deecb

Phase T.1: tournament pool play

Commit 7724a62

“Two robots in a match is a fight. A room full of people who each wrote a robot needs a tournament.” The format was designed on the project wiki, in plain words, before any code: pool play first, then a bracket.

Pools hold four robots, or three when the numbers don't divide evenly (nine robots make three pools of three, not 4 + 4 + 1). The engine never runs a battle itself. It is handed a function, “given these robots, this seed and this limit, who won?”, so the specs can script exact outcomes and the real battlefield plugs in later.

Intermission: where the tutorial meets the shipping code

Here is a confession the commit history makes on its own. The chapters above are a retelling. The project was first built in a hurry, the way projects are, and then rebuilt from scratch, one teachable commit at a time, so that a reader could follow it. Meanwhile the original line kept shipping. By the end of Phase W the two did the same things (the same language, battlefield, tournament, browser compiler and CI command) with different code.

Rather than pretend otherwise, the history swaps the tree for the shipping code in a single commit, at the point where the two reached the same features. The diff is large and teaches nothing line by line; what matters is what changes shape:

  • Battle::Field takes robots as {name, source} pairs and runs them on fibers itself; the separate Match class is gone.
  • The command line's match output reports cycles and a wins/ties table, and the engine has grown the CROBOTS behaviors the early robots lean on (dividing by zero gives zero, for one), so the same three robots from C.6 now produce a winner every time.
  • The test suite is the shipping one: fewer, broader specs (99 here, against 172 at W.6), including building the example robots as native programs.

Phase 5b-2: battle entirely in the browser, no server

Commit de88c3f

W.1's discovery comes due. If exceptions don't work on wasm32, neither can the battle engine's fibers be trusted once the page is in control. So src/battle/step_robot.cr gives each robot a second way to run with no fibers and no exceptions at all.

The trick is continuation-passing style. Everywhere the interpreter would say “work out this value, then do something with it”, it instead hands over a small function meaning “and here is what to do next”. Charging a cycle is the one place that does not call that function right away: it stores it and returns. The next turn picks up by calling the stored function. No exception, no fiber, just an ordinary return.

src/battle/step_robot.cr

private def tick(n : Int32, &after : -> Nil) : Nil
  return if @halted
  if n <= 0
    after.call
    return
  end
  @cycles += 1
  remaining = n - 1
  @resume = -> { tick(remaining, &after) }   # pause here; resume later
end

The parser also gains try_parse, which reports a syntax error as data instead of raising, so one robot's typo can't take down a whole battle. The page sends 2 to 4 robots and a seed into crystal-robots.wasm and gets back the standings and an animated SVG replay.

Chapter 9 · The robots start fighting as WebAssembly

For a long time the headline on the landing page, “robots you program, compiled to WebAssembly, fighting in your browser”, was only half true. The site compiled your robot and showed you the bytes, but the battle itself ran your robot through the interpreter. The reason goes back to C.1: the compiled code could count cycles with env.tick, but plain WebAssembly cannot pause in the middle of a function and pick up later, and a robot that can't pause can't take turns.

This chapter makes the breakpoints real, without relying on any browser-specific feature. The emitter learns a resumable mode: each function becomes numbered blocks run by a dispatch loop, and everything a paused robot needs to remember (where it was, its local variables, the half-finished parts of an expression) lives in its own memory instead of on WebAssembly's stack. Calling the module's step() runs exactly one CROBOTS cycle and returns. Then crystal-robots.wasm builds one such module per robot and lets the battlefield step them. The proof is the same idea as A.13's differential spec, scaled up: sixty seeded battles and a full tournament produce byte-for-byte identical results whether the robots are compiled or interpreted, and the compiled ones are faster.

A resumable WebAssembly emitter: compiled robots that pause at every cycle

Commit 2107a8c

Here is the problem stated plainly. The battlefield runs four robots in lockstep, one CROBOTS cycle each, round and round. A compiled robot is a WebAssembly function, and a WebAssembly function, once called, runs until it returns. There is no instruction for “stop here and carry on later”. Browsers are adding ways around that, but each one is a newer feature that only some browsers have, and this project wanted plain WebAssembly that runs everywhere, wasmer included.

So the emitter does the pausing itself. In resumable mode every function is cut into numbered blocks at each place a cycle is charged, and run by a loop that jumps to the saved block number. Nothing is left on WebAssembly's own value stack when a block ends: half-finished calculations go into local variables, and every call in progress keeps its block number, locals and temporaries in a 2 KB frame in the robot's own memory. Calling step() runs exactly one cycle, stores where it got to, and returns. Calling it again carries on, even from deep inside nested function calls. Recursion that goes too deep becomes the same robot error the interpreter reports, not a crash.

The proof reuses A.13's idea at full scale. Under wasmer, every bundled robot fights three seeds in two- and four-robot fields, once compiled and once interpreted, and every recorded frame, cycle count, restart, printed line and winner must match exactly. The modules grow about ten to fifteen times larger for it, which still means a few kilobytes.
